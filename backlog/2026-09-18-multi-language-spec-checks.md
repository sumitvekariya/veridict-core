# Multi-language spec checks: options

**Context:** the gate's job is to relate an implementation to its
specification, not to run tests written by the same model that wrote the code.
Today it does that for Python only: mypy, pytest, Z3 property scripts, and
crosshair against `pre:`/`post:` docstring contracts. Rust, Go, C, TypeScript
and Java pull requests pass through unchecked. This note lays out the ways to
close that gap so the roadmap can schedule a decision rather than a guess.

Any option must satisfy the constraints the current gate already meets:

- Runs in the reviewed repository's CI, never inside the issuer.
- Publishes a verdict the issuer can trust, today a GitHub Actions check run,
  later a `veridict verify` result.
- Produces a concrete counterexample on failure, because that is what makes the
  verdict reviewable by a human.
- Works on LLM-synthesized code without human proof engineering.
- Degrades to "nothing declared, nothing checked" rather than blocking repos
  that have not adopted contracts.

## Option A: one adapter per language, one verdict schema

Replicate the crosshair pattern in each ecosystem's native tool.

| Language | First choice | Why | Fallback |
|---|---|---|---|
| Rust | **Kani** | Bounded model checking on `cargo` projects, harness-based, maintained by AWS, already running in the Rust standard library's CI. Function contracts (`requires`/`ensures`) are an accepted experimental language feature being ported into std. | Verus for SMT-strength proofs; Prusti, Creusot |
| Go | **rapid + `go test -fuzz`** | No production-grade contract verifier. Property-based tests plus native coverage-guided fuzzing give counterexamples with zero toolchain cost. | Gobra (ETH, Viper-based, alpha; heavy JVM toolchain) |
| C, C++ | **CBMC** | Harness-based bounded model checking, in production CI at aws-c-common. | Frama-C WP with ACSL contracts (LLMs can now draft ACSL); KLEE or SeaHorn at LLVM IR |
| Java | **OpenJML** | JML contracts checked through SMT; the direct analogue of crosshair. | KeY (interactive) |
| TypeScript | **fast-check** | Dominant property-based testing library, integrates with Vitest and Jest; no mature contract verifier exists. | none |
| Python | crosshair | as today | Hypothesis |

**Trade-offs.** Each adapter is idiomatic and the counterexample property holds
everywhere: Kani, CBMC, OpenJML and crosshair return failing inputs, and
property-based tests shrink to one. The cost is N contract dialects, N
synthesis prompts, and uneven strength: Rust and C get bounded proofs, Go and
TypeScript get well-generated tests.

## Option B: one verified source language, transpiled

Synthesize in Dafny, verify there, compile to the target (Dafny targets C#,
Java, Go, Python and JavaScript). For Rust, synthesize in Verus.

**Evidence.** On the vericoding benchmark of 12,504 formal specifications, LLM
success is 82% for Dafny, 44% for Verus and 27% for Lean, and pure Dafny
verification success rose from 68% to 96% in a year.

**Trade-offs.** The strongest claim available, a machine-checked refinement
proof. But the shipped code is generated, not idiomatic, so the maintainer
cannot own it; C and Rust are outside Dafny's targets; and the whole repository
would have to adopt a proof language. Right as an optional tier for functions
the spec marks critical, wrong as the general gate.

## Option C: verify at LLVM IR

Compile C, C++ and Rust to LLVM IR and check with SeaHorn or KLEE. One backend
for the systems-language family, harnesses still written per language. Does
nothing for Go, Java, TypeScript or Python, so it is at most an implementation
detail inside Option A's C and Rust adapters.

## Option D: property-based testing as the universal floor

Hypothesis, proptest, rapid, fast-check, jqwik and RapidCheck cover every
language in scope. Specifications become properties in the code's own test
language, generated by synthesis. Weaker than symbolic or bounded checking and
dependent on generator quality, but it exists everywhere and always yields a
failing input.

## Option E: mutation testing as a strength check

cargo-mutants, mutmut, go-mutesting, Stryker and PIT measure whether the
generated tests can tell the implementation from a broken copy. This checks
test strength, not spec conformance, so it complements the others and cannot
replace them.

## Recommendation

**Option A as the architecture, with D as each adapter's floor and B as an
optional tier.**

1. Define the adapter contract first: a language adapter declares how it
   detects applicability, what it runs, and the verdict it publishes
   (pass, fail with counterexample, or nothing declared). The check run's
   summary carries per-adapter results, and the review page shows them.
2. Ship **Rust via Kani** as the first non-Python adapter. It has the largest
   overlap with the incidents that motivated Veridict, which were systems
   code, and contracts are entering Rust itself, so synthesized code can carry
   `requires`/`ensures` that the ecosystem will recognise.
3. Then Go (rapid plus fuzz), C (CBMC), TypeScript (fast-check), Java (OpenJML).
4. Teach synthesis each dialect as it lands. Research on LLM-drafted ACSL and
   JML suggests this is feasible, and it is where the effort goes.
